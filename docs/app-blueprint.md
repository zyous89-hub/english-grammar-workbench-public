# 앱 제작 청사진 — 학생 숙제 채점·어법 기록

갱신: 2026-09-24. 앱 구현 전 설계 문서입니다. 사용자 확정 방향, 시험으로 확인한 범위, 구현 제안을 구분합니다. 근거: [제품 목표](product-goals.md), [이번 대화](conversations/2026-09-24-010.md), [경계 추적 시험](verification/2026-09-24-adaptive-repeat-ocr.md).

## 1. 사용자 확정 목표와 채택 방향

- 2026-09-24 후속: 사용자가 **기존 소형 모델을 활용하는 방향**으로 진행하자고 선택했습니다. 최근 논의 범위는 로컬 유형 판별기입니다. 구체 모델·정확도·추가 학습은 미확정입니다. Jev도 포함되는지 질문했으며, 공식 제공 경로가 외부 API이고 로컬 가중치 배포는 확인하지 못했으므로 현재 로컬 후보에 포함하지 않습니다. API사용을 승인한 것으로 해석하지 않습니다. [대화017](conversations/2026-09-24-017.md)

- **2026-09-24 확정: 문제 유형 판단은 학생 숙제 스캔 대신 필기 없는 문제 원본을 사용합니다.** 원본 첫쪽의 인쇄 지시문·선지·배치를 판별 입력으로 삼고 학생 이름·필기·성적을 사용하지 않습니다. 원본이 없으면 학생 자료를 외부로 자동 전송하는 대체 동작을 하지 않습니다. 분류를 맡길 엔진·혼합/보류 처리 세부 방식은 별도 미정입니다. [대화016](conversations/2026-09-24-016.md)

- 폴더1은 학생 숙제 JPG, 폴더2는 해당 숙제의 PDF 답지입니다. 한 세트는 학생 한 명의 1회분 숙제입니다.
- M1은 독립 실행 앱 안에서 채점·기록, M2는 틀린 어법 구분·추가 기록입니다. 실행 중 학생 데이터를 외부로 보내지 않는 방향을 따릅니다. 내장 로컬 OCR을 검토 중이며 특정 엔진의 최종 채택·패키징 완료를 뜻하지 않습니다.
- 편집 가능한 로컬 HTML 기록을 우선합니다. Google Drive 업로드는 앱의 자동 동작으로 넣지 않습니다.
- 사용자는 ‘단어가 있는지를 판별할 수 있으면’ 현재 경계 추적 방식을 추후 앱 채점 과정에 사용하도록 요청했습니다. 따라서 필기 존재를 확인하고 획을 따라 영역을 복원하는 방식을 답안 추출 설계에 반영합니다. 필기 존재만으로 정오답을 판정하지 않습니다.
- 오답→정답 왜곡은 허용하지 않는 요구입니다. 이것은 검증 목표이며 지금 보장한 성능이 아닙니다. 정답→오답도 최종적으로 줄여야 합니다.
- 한 세트의 실제 수동 채점 시간은 사용자 추후 제공입니다. 마감은 2026-09-28 오전(KST), 정확한 시각은 미정입니다.

## 2. 답안 추출 흐름 — 구현할 설계

1. 파일·페이지·문항·답란을 연결하고 원본을 보존합니다. 유형 판단에는 필기 없는 문제 원본을 사용합니다. PDF에 사용 가능한 텍스트가 있으면 직접 추출하고 없으면 로컬 OCR로 읽는 경로는 구현 제안입니다.
2. 필기 없는 문제 원본과 학생 스캔을 정렬합니다. 원본에서 인쇄 글자 줄과 답란 밑줄을 찾습니다.
3. 밑줄 전체 가로 범위로 답란을 잡되 오른쪽 문항 번호가 섞이지 않도록 끝을 제한합니다. 위쪽은 이전 밑줄뿐 아니라 인쇄 글자 줄도 경계로 씁니다.
4. 현재 위 경계에 필기 후보 획이 걸리면 연결된 획을 따라 위 경계를 한 픽셀씩 올립니다. 답란 가로 범위의 원본 인쇄 글자 앞에서 멈춥니다. 획이 이어지지 않으면 불필요하게 확장하지 않습니다.
5. 원본을 뺀 차이 영상은 필기 후보 위치 찾기에 사용하고, OCR에는 학생 원래 이미지의 잘라낸 영역을 전달하는 경로를 기본 후보로 둡니다. 확장 전후 좌표와 입력 이미지를 남깁니다.
6. 필기 존재 여부와 OCR 문자열을 따로 기록합니다. 필기 후보가 있는데 문자열이 비면 무응답으로 처리하지 않습니다. 후보가 없더라도 희미한 필기·정렬 실패 가능성을 먼저 검증해야 합니다.
7. OCR 원시 출력을 보존하고, 불확실한 판독·취소선·복수 답·윗줄과 붙은 획은 교사 확인으로 보냅니다. 점수가 높다는 이유만으로 정답 확정하지 않습니다.
8. 판독이 확인된 학생 답만 해당 문항의 답지·교사 확정 허용 답과 비교합니다. OCR 단계에서 답지에 맞춰 철자를 교정하지 않습니다.
9. M1 기록을 저장하고, M2는 확인된 채점 결과에 어법 분류를 연결합니다. 기존 어법 스킬·분류표의 확인 범위는 [스킬 이식표](skill-mapping.md)를 따릅니다.

**추가 입력 결정 필요:** 현재 방법에는 필기 없는 문제 원본이 필요합니다. 실제 시험에는 학생 JPG·문제 원본 PDF·답지가 제공됐지만 원래 제품 정의는 두 폴더입니다. 문제 원본을 교재 등록 때 따로 받거나 폴더2의 보조 파일로 받는 방식은 아직 확정하지 않았습니다. 답지만으로 항상 원본을 대체할 수 있다고 가정하지 않습니다.

## 3. 확인된 범위와 아직 해결되지 않은 것

| 항목 | 실제 상태 |
|---|---|
| 필기 획 연결을 따른 경계 복원 | 2-2에서 1px씩 총7px 복원, 윗줄 인쇄체 미혼입을 시각 확인 |
| ‘단어가 있다’는 판별 | 현재는 어두운 픽셀·연결 성분에 의한 필기 후보 검출. 단어/잡음 구분의 범용 성능 미검증 |
| 복원 후 정확한 전사 | 2-2는 여전히 실패. 영역 복원과 인식 성공을 구분 |
| 적용 범위 | 경계 추적은 2개 답란 시험. 전체83칸·새 페이지 회귀 검증 필요 |
| 동일 입력 반복 | 4-3 새 프로세스10회 출력·점수 동일. 무작위 샘플링 아님 |
| 밑줄 문자 혼입 | 모델의 문자 선택에서 발생. 무조건 삭제하는 규칙 미채택 |
| 흰 여백 복원·밑줄 제거 | 진단용 시험만 수행. 공통 전처리에 미적용, 필기 훼손 여부 추가 검증 필요 |
| 채점·학습·앱 | 답지 미열람, 실제 채점·추가 학습·앱 구현 모두 미실시 |

현재 시험의 픽셀 임계값·연결 크기를 모든 해상도에 그대로 고정하지 않습니다. 학생 글씨가 윗줄 인쇄체와 맞닿거나 겹치면 ‘손글씨 보존’과 ‘윗줄 제외’를 동시에 충족하지 못할 수 있으므로 확인 대상으로 남깁니다.

## 4. 첫 구현 단위 — 제안

### 유형별 인식 모델 분리 — 2026-09-24 사용자 제안, 검토 단계

근거: [대화013](conversations/2026-09-24-013.md). 객관식이면 숫자·선택 표기에 맞는 모델, 주관식이면 손글씨 문자·문장에 맞는 모델을 불러오는 방향을 설계 후보로 추가합니다. **유형을 어떻게 판단할지는 다음 대화 이후 결정하라는 사용자 지시에 따라 미정으로 둡니다.** 분류기·자동 판단 규칙·사용자 선택 방식 중 어느 것도 이번에 확정하지 않습니다. 기존 모델 최종 채택이나 새 학습 착수를 뜻하지 않습니다.

처리 역할은 유형 확인 → 답안 위치 추출 → 유형별 인식 → 불확실한 판독 확인 → 답지·문항 기준 비교 → 기록으로 구분하는 안을 제안합니다. 숫자 모델도 인쇄된 문항·선지 번호와 학생 답을 구분할 영역 정보가 필요합니다. 현재 객관식2번처럼 답안이 잘려 들어가면 출력 문자 집합을 숫자로 좁히는 것만으로 복구되지 않습니다. 비숫자·잡음·판독 불가를 보류할 수 있어야 하며 모든 입력을 억지로 숫자로 만들지 않습니다. 복수 선택·취소/수정 표기도 한 자리 숫자로 강제하지 않습니다.

주관식 모델은 실제 쓴 철자와 문장을 읽고, 정오답 판정은 검토한 답지·허용 답·문항 조건으로 별도 수행합니다. 유형별 모델 분리의 성능 이점은 아직 시험하지 않았습니다. 앞선 객관식9개 일치는 수동 영역 조건이며 원본 기반 추출에서는2번이 실패한 사실을 유지합니다.

### 첫 페이지로 시험지 유형 제안 — 원본 사용 확정, 판별 엔진 미정

2026-09-24 후속 승인으로 아래 제안 중 **유형 판단 입력을 문제 원본으로 삼는 부분은 확정**했습니다. 남은 일정의 로컬AI 가능성은 [검토 기록](local-classifier-feasibility.md)을 따릅니다. 기존 모델 활용 시제품과 새 모델 학습·독립 성능 검증·전체 앱 완성을 구분합니다.

후속으로 사용자가 외부LLM API·Jev API·직접 구현의 비용/보안 비교를 요청했습니다. [공식 문서 조사와 비교](type-classifier-options.md)를 따릅니다. 새 방향 채택이나 외부 전송 허용은 아직 확정하지 않았습니다.

[대화014](conversations/2026-09-24-014.md): 사용자는 한 시험지의 유형이 대체로 이어진다고 설명하며 첫 페이지를 기본 OCR로 읽고 별도 주체가 시험지 유형을 결정하는 흐름을 검토 중입니다. assistant는 OCR 텍스트·위치에서 지시문과 선지 배열을 함께 보는 **로컬 규칙 기반 판별기 + 불확실할 때 교사 확인**을 우선 후보로 제안했습니다. 아직 사용자 채택·구현·실제 판별 성능 검증은 없습니다.

객관식 단서 예시: 고르라는 지시와 가까이 배치된 반복 선지 묶음. 주관식 단서 예시: 직접 쓰기·고쳐 쓰기 지시와 답란 배치. 예시는 규칙 초안이며 번호만 또는 밑줄만으로 결정하지 않습니다. 객관식에도 빈칸이 있고 주관식에도 소문항 번호가 있습니다. 보기·예제를 실제 응답 문항과 구분하는 문제도 남습니다. 단서 부족·충돌·유형 혼합은 보류 상태를 두는 안입니다. 첫쪽 결과를 시험지 기본값으로 사용하되 뒤쪽에서 반대 단서가 발견되면 확인하는 흐름도 제안 단계입니다.

### 첫 화면·저장 단위 상세

첫 단위는 **원본·학생 페이지를 연결해 답란을 추출하고 교사가 판독을 확인하는 화면**입니다. 입력 조각, 이전/현재 경계, OCR 원문, 교사 수정 전사를 한 문항에서 확인·저장하도록 합니다. 채점 기능은 확인된 전사와 검토한 답지를 연결한 뒤 구현합니다. 이번 문서 작성은 앱 구현 착수나 완료를 뜻하지 않습니다.

최소 기록 항목 제안: 세트·페이지·문항·답란 ID, 입력 식별값, 경계 좌표·확장 사유, 필기 후보 상태, OCR 원문·모델 버전·점수, 교사 전사·확인 상태, 답지 근거, 채점 상태, 수정 이력. 개인정보와 실제 답안은 로컬에 두며 Git에는 비식별 설계·검증 요약만 남깁니다.

검증은 같은 개발 표본의 수정 전후 비교와 별도 학생·페이지 평가를 구분합니다. 필기 누락, 윗줄 혼입, 획 절단, 철자 변형, 취소선 오인, 무응답 오판, 오답→정답 왜곡을 각각 확인합니다. 자동 판독·교사 확인을 포함한 전체 업무 시간은 실제 수동 시간 제공 후 비교합니다.

### 소형 로컬 모델 후보 비교 — 2026-09-24

사용자 요청에 따라 [후보 장단점과 시험안](local-model-shortlist.md)을 작성했습니다. assistant 권고는 Qwen3-4B-Instruct-2507 우선 시험, Qwen3.5-2B 비교입니다. 특정 모델 최종 채택·설치·성능 검증은 아직 없습니다. 원본 유형 판별에만 사용하고 학생 필기 교정과 구분합니다.

### 다른 PC 배포 — 제안, 미검증

[대화020](conversations/2026-09-24-020.md): Windows x64 우선, CPU 기본 호환 경로·GPU 선택 가속, 모델과 OCR 실행 환경을 포함하는 오프라인 설치본을 제안합니다. 대상 PC의 최소 사양·속도·깨끗한 환경 설치·통신 차단 검증 전이며 확정 지원 사양이 아닙니다. 원본 유형 판별 결과는 교재·판본·입력·설정에 묶어 재사용하는 안입니다. 지원하지 않는 PC에서 외부 API로 자동 전환하지 않습니다.

### 학생 자료 로컬 유지·원본 유형 판단 API — 후속 조건

[대화021](conversations/2026-09-24-021.md)에서 사용자는 학생 데이터가 외부로 나가지 않는 조건이면 API 사용에 긍정적으로 답했습니다. 학생 OCR·전사·성적은 로컬에 두고 별도 원본에서 유형 판단에 필요한 지시문·선지 구조만 API로 보내는 안을 제안합니다. 원본에도 학생 식별 정보가 없는지 검사하며 파일명·메타데이터·로그를 통한 전송도 제외합니다. 모델·비용 한도 미정, 실제 API 사용·전송 없음. 기존 소형 로컬 모델 선택은 최종 확정된 것으로 간주하지 않습니다.

현 CPU OCR의 23개 조각 인식 자원 실측은 대화021에 기록했습니다. Windows x64·최근 4코어 이상 CPU·RAM8GB부터 검증, RAM16GB·SSD를 여유 사양 목표로 제안하지만 전체 앱 최소 사양·처리 속도는 미검증입니다.

### 원본 선지 기준 객관식 인식 — 후속 정정·제안

[대화023](conversations/2026-09-24-023.md): 사용자가 승인한 대로 원 모양은 답안 검출 필수 조건에서 제외합니다. 앞선 ‘원으로 둘러쓴 번호부터’ 범위 제안을 전체 입력 조건으로 적용하지 않습니다. 기존 원형 성분 탐색 실험은 과거 개발 기록이며 일반 해법으로 채택하지 않습니다.

원본 지시문·선지 배열에서 문항 유형과 단일/복수 선택 조건을 파악하고 문항별 선지 번호·내용·영역을 등록하는 안을 제안합니다. 정렬된 학생 페이지의 추가 표시를 선지 위치에 연결하거나 별도 필기 숫자를 인식합니다. 동그라미·체크·번호만 쓰기 등을 원 모양에 종속시키지 않습니다. 밑줄·메모·취소선과 최종 선택의 구분은 별도 검증하며 근처 선지로 무조건 배정하지 않습니다. 답지 정답을 학생 선택 판독에 사용하지 않고 애매한 경우 보류합니다. 원본 구조 분석에 API를 쓰더라도 학생 선택 판독은 로컬에 유지합니다. 코드·학습·성능 검증은 아직 미실시입니다.

### 객관식 채점 규격 초안

[객관식 채점 규격](multiple-choice-grading-spec.md)에 문항·선지 등록, 학생 선택 판독, 답지 비교, 보류와 교사 수정 기록을 정의하는 초안을 작성했습니다. [대화024](conversations/2026-09-24-024.md)의 사용자 후속 답변으로 점수·배점·부분점수 계산 없음, 단일 선택의 명백한 복수 응답은 오답 처리가 확정됐습니다. 나머지 제안 전체를 확정 요구로 취급하지 않습니다. 구현·학습·성능 시험은 미실시입니다.

## 5. 추가 학습 — 설명 및 향후 제안, 미실행

필기 이미지와 교사가 확인한 실제 문자열을 짝지어 학습하는 것은 지도학습입니다. 기존 OCR의 가중치를 추가로 조정하면 미세조정이라고 합니다. 이번 설명의 학습은 보상을 주어 행동을 바꾸는 강화학습이 아닙니다. [PaddleOCR 공식 데이터 형식](https://paddlepaddle.github.io/PaddleOCR/main/en/datasets/ocr_datasets.html)은 이미지 경로와 문자열 라벨을 짝으로 사용합니다.

‘학생의 의도’가 실제 쓴 문자에 대한 확인이라는 뜻이면 방향이 맞습니다. 그러나 의도했을 법한 올바른 철자로 바꾸면 안 됩니다. 설명용 가상 예시: 실제 필기가 `beter`이면 라벨도 `beter`이고 `better`로 고치지 않습니다. 이는 실제 학생 표본의 전사가 아닙니다. 판독 불가 자료는 추정 라벨로 학습시키지 않습니다.

사용자 후속 설명으로 의미를 명확히 했습니다: **학생이 a를 썼지만 모양이 u처럼 보이는 경우, 쓴 문자가 a로 확인됐다면 학습 라벨은 a입니다.** 사용자가 말한 ‘학생의 의도’는 이런 글자 정체의 확인입니다. 외형이 u처럼 보인다는 이유만으로 u를 라벨로 고정하지 않습니다. 이는 글씨체 오인식 교정이며 단어의 철자 오류를 정답 단어로 수정하는 것과 구분합니다. 앞선 assistant 설명은 의도를 단어 전체 교정으로 넓게 해석했으므로 이 후속 설명을 우선합니다. 위 예시는 개념 설명이며 특정 학생 표본의 확정 전사가 아닙니다.

다양한 학생의 정답·오답 철자와 필기 형태를 포함하고, 학습에 쓰지 않은 학생·페이지로 성능과 회귀를 평가하는 방안을 제안합니다. 학습 자체의 착수·데이터 수량·일정은 아직 확정하지 않았습니다.
