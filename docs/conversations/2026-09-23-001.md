- 원문 여부: 현재 대화에서 보이는 문장을 그대로 옮김. 아래 제목·번호·메타데이터만 추가.

- 이전 대화: 이 파일에 원문 수록하지 않았으며 `../context-before-log.md`는 요약임.
- 저장 범위: 로컬 Git. GitHub 원격 저장 아님.
- 채팅 화면용 인용과 sandbox 링크는 원문 그대로 보존. 외부 출처는 `../sources.md` 참고.

## 메시지 004 — assistant (진행 알림)

현재 GitHub 연결에는 저장소 생성·커밋 기능이 없고, 별도의 업로드 경로도 확보되지 않았습니다. 우선 지금 대화와 개발·검증 기록 양식을 담은 로컬 Git 저장소를 만들어 드리겠습니다. 아직 GitHub에 저장된 것은 아닙니다.

## 메시지 005 — assistant (진행 알림)

첫 기록부터 사용자님이 정한 조건과 제가 제안한 설계를 구분하겠습니다. 아직 하지 않은 구현·시험은 미완료로 표시하고, 이후 코드 변경과 검증 결과를 연결할 수 있게 구성하겠습니다.

## 메시지 006 — assistant (최종 답변)

**좋습니다. ‘개발 과정이 보이는 저장소 + 검증된 최종 결과물’로 구성하는 것을 추천합니다.** 다만 대화량 자체보다 **사용자님이 무엇을 결정했고, 그 결정이 코드와 시험 결과에 어떻게 반영됐는지**를 보여주는 것이 핵심입니다.

먼저 저장 상태를 정확히 말씀드리겠습니다. 연결된 GitHub 계정은 `zyous89-hub`로 확인했습니다. 하지만 **현재 이 대화의 GitHub 도구에는 저장소 생성·커밋 기능이 없고, 별도의 인증된 업로드 경로도 확보되지 않았습니다.** 따라서 GitHub에 저장했다고 말씀드릴 수는 없습니다.

대신 **이번 요청과 답변, 요구사항, 설계 결정, 검증 계획을 담은 로컬 Git 저장소를 만들고 초기 커밋까지 완료했습니다.**

## 1. 이 방식이 포트폴리오에 적합한 이유

SK하이닉스는 이번 대회에서 문제 정의, AI 활용, 결과 검증 과정을 평가한다고 설명합니다. 따라서 결과물만 보여주는 것보다, **그 결과물이 만들어진 판단과 검증을 함께 제시하는 방향이 평가 취지에 맞는다**는 판단입니다. citeturn244653search0

Cofa-Probe도 완료 기준이 명확한 지시, 실패 후 수정·재검증한 기록, 선택 이유와 기각한 대안, 실제 결과물과 일치하는 설명을 평가 신호로 제시합니다. 다만 우리가 만드는 개발 기록은 **공식 Probe 평가 기록을 대신하는 것이 아니라, 지원 경험을 설명하는 자체 증거**입니다. citeturn659695view2

우리 프로젝트에서는 다음 연결이 보여야 합니다.

> **사용자 요구 → AI의 제안 → 사용자 판단 → 코드 변경 → 시험 → 결과와 한계**

예를 들어 지금까지 확인된 요구는 “어법 해설은 있지만 분류는 없다”, “완성 앱은 AI 없이 실행한다”입니다. 이에 대한 규칙 기반 분류·교사 확인 구조는 제안이고, 실제 구현과 성능 검증은 아직 남아 있습니다. **이 세 상태를 구분해서 기록하는 것부터 시작했습니다.**

## 2. 대화 원문과 심사용 요약을 나눠 두겠습니다

저장소의 주요 구성은 다음과 같습니다.

| 위치 | 역할 |
|---|---|
| `README.md` | 프로젝트 목적, 현재 상태, 읽는 순서 |
| `docs/conversations/` | 이번 요청부터의 사용자·assistant 대화 기록 |
| `docs/decisions/` | 선택한 방법, 이유, 다른 대안, 미정 사항 |
| `docs/evidence-index.md` | 요구·결정·코드·시험 결과를 연결하는 표 |
| `docs/evaluation-plan.md` | 비교 방법, 평가 자료, 측정 지표 |
| `src/`, `rules/`, `tests/` | 앞으로 구현할 앱·규칙·시험의 위치 |
| `portfolio/` | 최종 제출용 요약과 결과물의 위치 |
| `AGENTS.md` | 개발 도구가 이어서 작업할 때 읽을 프로젝트 안내 |

현재 소스·규칙·시험 폴더에는 **미구현 상태를 밝힌 안내문만** 있습니다. 기존 스킬의 원문이나 실제 답지도 이번 패키지에 들어 있지 않습니다.

**대화는 원문으로 보관하되, 심사자에게 대화 전체를 읽으라고 요구하지 않는 구성**이 좋습니다. 제출용 요약에서는 중요한 결정과 실패·수정 사례를 골라 설명하고, 해당 대화·코드·시험 기록으로 연결하겠습니다.

기록 시작 전의 논의는 별도 ‘이전 맥락 요약’으로 정리했습니다. 이를 과거 전체 대화의 원문이라고 표시하지 않았습니다.

## 3. ‘전부 저장’에도 지켜야 할 기준이 있습니다

**첫째, 사용자님과 제가 실제로 주고받은 발화를 기록합니다.** AI의 제안을 사용자님이 승인한 것처럼 쓰거나, 나중에 그럴듯한 개발 과정을 만들어 넣지 않습니다. 잘못된 제안과 정정도 남깁니다. 실제 실행하지 않은 시험은 ‘미실시’로 표시합니다.

**둘째, 비밀값과 학생 개인정보는 원문 그대로 올리지 않습니다.** 필요한 가림 처리는 위치와 이유를 표시하고, 시험지·답지의 공개 가능 범위도 따로 확인하겠습니다. Git에 들어간 민감정보는 파일을 지운 뒤에도 이력이나 다른 사본에 남을 수 있으므로, 처음부터 제외하는 편이 안전합니다. citeturn232598view4

**셋째, 초기 저장소는 비공개로 시작하는 것을 추천합니다.** 공개할 자료를 검토한 뒤 제출용 공개본이나 별도 증거 패키지를 준비하면 됩니다. 비공개 저장소는 주소만 알려준다고 심사자가 열 수 있는 것은 아닙니다. citeturn659695view1

**넷째, 자동 동기화가 켜진 것은 아닙니다.** 대화 파일 작성, 로컬 커밋, GitHub 업로드는 별개의 단계입니다. 이 대화가 끝난 뒤나 다른 대화에서 나눈 내용이 저절로 저장되지는 않습니다. 작업할 때마다 실제 저장된 범위를 확인해야 합니다.

## 4. 실제 제출은 ‘요약 파일 + 근거’ 형태로 잡겠습니다

**GitHub 주소만 제출하는 방식으로 전제하지 않는 것이 좋습니다.** 앞선 공식 FAQ 확인 기록에서는 포트폴리오가 파일 1개·50MB 이하이며 URL 단독 제출은 불가했습니다. 이번에는 해당 페이지에 재접속하지 못했으므로, 이 조건의 최신 상태는 재확인하지 못했습니다.

그 조건이 유지된다면, **요약 PDF를 중심으로 하거나 허용 형식에 맞춰 결과물과 함께 하나의 ZIP으로 묶는 방식**을 검토하겠습니다. GitHub는 상세 근거를 제공하는 역할입니다. 외부 링크를 열거나 앱을 실행하지 않아도 핵심 내용을 이해할 수 있게 해야 합니다.

요약 자료에는 문제와 목표, 실제 사용 화면, 사용자님과 AI의 역할, 실패·수정·재시험 사례, 측정 결과와 한계를 담겠습니다. 제출 시점의 코드 버전도 함께 기록해, 설명한 결과와 실제 결과물이 맞도록 관리하는 것이 좋습니다.

## 5. 지금 만든 저장소를 GitHub로 올리는 방법

압축을 풀면 `english-grammar-workbench` 폴더가 나옵니다. **초기 이력이 담긴 `.git` 폴더도 포함**되어 있습니다. Git과 GitHub CLI가 설치되고 본인 계정으로 로그인된 PC에서, 해당 프로젝트 폴더의 터미널에서 다음 명령으로 비공개 저장소 생성과 첫 업로드를 진행할 수 있습니다. 같은 이름의 저장소가 이미 있다면 덮어쓰지 말고 먼저 확인해야 합니다. citeturn232598view2

```powershell
gh repo create zyous89-hub/english-grammar-workbench --private --source . --remote origin --push
```

로그인 확인, 오류 시 주의사항, 업로드 후 로컬·원격 커밋 비교 방법은 패키지의 `docs/github-setup.md`에 넣었습니다. **위 명령은 아직 실행되지 않았고, GitHub 저장소도 아직 생성되지 않았습니다.**

**방향은 좋습니다. 이제 포트폴리오를 위해 별도로 과정을 꾸미는 것이 아니라, 실제 개발하면서 생기는 요구·판단·실패·검증을 그대로 근거로 남기는 방식으로 진행하면 됩니다.**
