# JPG·PDF 입력, 인식 방법, 기록 저장 검토

확인일: 2026-09-23. 상태: 공식 문서 조사에 따른 추천안. 사용자 표본 시험·설치·인식 실행은 하지 않았습니다. 근거 대화: [007](conversations/2026-09-23-007.md).

후속 확인: 사용자는 OCR에 학습 모델이 쓰인다는 점을 몰랐다고 설명하며 **스탠드얼론 + 외부 데이터 송출 없이 기능하는지** 질문했습니다. 답변은 ‘내장 로컬 OCR로 구현 경로가 있다’입니다. 특정 엔진 선택·실제 보안/정확도 검증 완료를 뜻하지 않습니다. 자세한 요구 해석은 [D-007](decisions/0007-local-ocr-boundary.md)을 참고합니다.

## 추천 요약

| 항목 | 추천 | 아직 확인할 것 |
|---|---|---|
| 학생 숙제 | 현재 JPG 업무 유지 | 실제 해상도·기울기·손글씨·문항 형태 |
| 답지 | 제공 PDF 유지, 사용자가 JPG로 바꿀 필요 없음 | 텍스트형/스캔형/혼합형, 문항과 해설 배치 |
| 인식 | 답지 텍스트 추출 + 페이지/답안 위치 연결 + 손글씨 인식을 분리 | 내장 로컬 OCR 모델 허용 여부, 실제 정오답 판정 성능 |
| 원본·기록 | 앱 내부 로컬 저장을 기본으로 추천 | 암호화·백업·복구 설계와 실제 검증 |
| 공유 보고서 | 필요한 결과만 PDF/HTML로 내보내기; Google Docs는 선택 기능 후보 | 누구와 무엇을 공유할지, 계정·권한 정책 |

입력 형식은 이번에 사용자가 설명한 실제 업무 조건입니다. OCR·저장 방식은 아직 승인된 구현 결정이 아닙니다.

## 1. 학생 숙제 JPG를 PDF로 바꿔야 하는가?

바꿀 필요 없이 JPG를 직접 입력받도록 설계하는 것을 추천합니다. JPG를 PDF에 넣는 것만으로 손글씨가 텍스트로 바뀌거나 인식 품질이 올라가지는 않습니다. PDF로 묶으면 한 세트를 한 파일로 관리하기는 편하지만, 현재 스캔 업무를 바꿔야 할 인식상의 근거는 아직 없습니다.

원본 JPG는 그대로 보존하고, 앱이 인식용 복사본에 회전·기울기 보정·영역 자르기를 수행하는 안입니다. 반복 JPG 저장은 피하고 내부 중간 이미지는 메모리/무손실 이미지로 처리하는 방향을 검토합니다. 폴더의 파일 순서만 믿지 않고 인쇄 쪽·문항 번호와 실제 숙제 범위를 연결해야 합니다.

PDF도 이미지 묶음일 수 있다는 구분은 [pypdf 공식 문서](https://pypdf.readthedocs.io/en/stable/user/extract-text.html#digitally-born-vs-scanned-pdf-files)를 참고했습니다. 변환 필요성 판단은 해당 구분과 현재 JPG 업무에 근거한 설계 판단입니다.

## 2. 답지 PDF를 JPG로 바꿔야 하는가?

**사용자가 사전 변환할 필요는 없습니다.** 앱이 원본 PDF를 보관하고 페이지마다 처리 경로를 고릅니다.

1. 텍스트형 PDF: 문자·위치 정보를 직접 추출하고 화면과 대조합니다.
2. 이미지뿐인 스캔 PDF: 필요한 페이지/영역을 앱 내부에서 이미지로 렌더링한 뒤 인식합니다. 별도 JPG 파일을 사용자에게 만들라고 요구하지 않습니다.
3. 혼합형 또는 기존 OCR 텍스트가 있는 PDF: 페이지별로 추출 품질·원본 이미지 일치를 확인합니다. 텍스트가 있다는 것만으로 정답을 확정하지 않습니다.

숫자·정답 기호·다단 편집·줄바꿈과 문항/해설의 연결은 별도로 검증해야 합니다. PDF 전체를 먼저 이미지화하면 원래의 텍스트 정보를 활용하지 못하므로 텍스트형에는 권하지 않습니다. [pypdf: OCR와 직접 추출 비교](https://pypdf.readthedocs.io/en/stable/user/extract-text.html#ocr-vs-text-extraction)

## 3. 인식과 채점은 서로 다른 단계입니다

권장 분해: 파일 읽기 → 쪽/문항/답지 연결 → 학생 답안 영역 추출 → 문자·표시 인식 → 허용 답 기준 비교 → 판정·근거 기록 → M2 어법 연결.

| 기술 후보 | 적합한 역할 | 한계·조건 |
|---|---|---|
| PDF 텍스트 추출 | 텍스트형 답지 읽기 | 학생 손글씨를 읽는 기술이 아님; 배치·정답 연결 검증 필요 |
| 규칙 기반 영상 처리·표식 판독 | 정해진 위치의 체크/선택 표시, 페이지 정렬 후보 | 지정 양식과 실제 표식 검증 필요; 자유 손글씨 문장 인식의 대체재가 아님 |
| Tesseract | 인쇄된 영어/한국어 인식의 비교 후보 | 공식 FAQ도 손글씨 성능 한계를 밝힘; 주 손글씨 엔진으로 확정하지 않음 |
| PaddleOCR 등 로컬 인식 모델 | 인쇄문자와 손글씨 인식 후보 | 모델·언어·환경별 검증 필요; 학습된 AI이며 정확도 미확인 |
| 인식 엔진 자체 신규 개발 | 기존 엔진으로 해결하지 못하는 문제의 장기 연구 후보 | 표본·정답 전사·학습/평가 데이터가 없어 현재 처음부터 만드는 것을 추천하지 않음 |

[Tesseract FAQ](https://tesseract-ocr.github.io/tessdoc/FAQ.html#can-i-use-tesseract-for-handwriting-recognition)는 인쇄문자용 설계라고 명시합니다. [PaddleOCR PP-OCRv5 설명](https://paddlepaddle.github.io/PaddleOCR/v3.0.0/en/version3.x/algorithm/PP-OCRv5/PP-OCRv5.html)은 영어 손글씨를 지원 시나리오로 포함합니다. 이는 이번 학생 숙제에서의 성능 입증이 아닙니다. 특정 모델을 최신/최적이라고 확정하지 않았습니다.

PaddleOCR는 [로컬 모델 경로를 지정한 추론](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/OCR.html)을 지원합니다. 따라서 별도 앱을 사용자가 조작하지 않도록 내장하는 개발 경로는 있습니다. 다만 모델/실행환경 배포·라이선스·자동 다운로드 제거·네트워크 차단 검증은 별도 작업입니다. Tesseract의 LSTM 방식과 PaddleOCR를 ‘비AI’라고 부르지 않습니다.

### 기존 조건과 충돌할 수 있는 부분

- **외부 프로그램 조작 없음**: 앱 안에 인식 구성요소를 포함하는 방식으로 검토 가능.
- **학생 자료의 외부 전송 없음**: 로컬 처리·외부 호출 제거 후 실제 네트워크 차단 시험으로 검증할 조건.
- **학습된 AI도 전혀 없음**: 로컬 OCR 모델도 금지하는 엄격한 조건. 범용 손글씨 자동 채점을 충족한다고 현재 약속할 수 없음.

추천은 **외부 전송·생성형 AI 없이, 내장된 로컬 문자 인식만 사용하는 범위**입니다. 질문에 사용자는 ‘스탠드얼론 + 외부 데이터 송출 없음’이 가능한지 되물었습니다. 로컬 모델 방식은 그 조건을 목표로 구현할 수 있지만 특정 모델 도입은 아직 하지 않았습니다. 기존 ‘AI 없음’을 외부 서비스/송출 금지와 모든 학습 모델 금지 중 어느 의미로 적용할지는 이번 설명을 반영해 정리 중이며, 과거 문구만으로 OCR 전체를 금지하거나 무단으로 채택하지 않습니다.

설치본에 엔진·모델·필수 라이브러리를 모두 포함하고, 실행 중 모델 다운로드·클라우드 대체 처리·사용 통계·오류 내용 업로드·자동 업데이트 경로를 없애는 구성을 제안합니다. 앱 사용자는 별도 OCR 프로그램·Python·데이터베이스 관리 도구를 직접 설치하거나 실행하지 않는 것이 목표입니다. 개발 때 필요한 도구와 사용자 실행 조건은 구분합니다.

검증은 (1) 새 대상 환경에서 오프라인 설치/실행, (2) 네트워크 차단 상태에서 입력→인식→채점→저장, (3) 앱과 하위 프로세스의 연결 시도 관찰 및 코드/설정 점검을 나눠 수행해야 합니다. 차단된 상태에서 작동한다는 사실만으로 외부 통신을 시도하지 않는다고 입증되지는 않습니다. 외부 전송 없음은 아직 시험하지 않은 배포 기준입니다.

### 반드시 확인할 실패 유형

학생이 실제로 잘못 쓴 영어를 OCR가 그럴듯한 정답으로 고쳐 읽으면 채점이 틀립니다. 인식 문자와 원본 영역을 함께 남기고, 맞춤법 자동 교정으로 원문을 바꾸지 않는 설계를 제안합니다. 지움·겹쳐 쓰기·화살표 이어쓰기·빈칸/무응답도 따로 확인해야 합니다. 인식 점수만으로 정답을 보증할 수 없습니다.

실자료를 받으면 같은 개발 표본에서 PDF 추출/문항 연결, 문자 인식 오류, 최종 채점 오류, 자동 판정 비율, 교사 확인 시간, 세트당 전체 시간을 구분해 비교합니다. 읽기 불가·연결 실패를 오답과 분리합니다. 수동 채점 기준 시간은 여전히 사용자 추후 제공입니다. 정확도와 처리 시간은 아직 측정하지 않았습니다.

## 4. Google Docs와 로컬 기록 비교

기록의 저장소와 사람이 읽는 보고서 양식은 구분하는 것을 추천합니다. 문항별 판정·어법·수정 이력은 구조화해 저장하고 보고서는 그 기록에서 생성하는 방식입니다.

| 방식 | 장점 | 보안·운영상 고려 | 추천 역할 |
|---|---|---|---|
| 앱 내부 로컬 기록(SQLite 등) | 서버 없이 문항·세트·어법 기록 연결과 검색 가능 | PC 접근/분실·악성코드·백업 관리 필요. 파일 자체가 자동 암호화되지는 않음 | 기본 원본 기록 저장소 |
| 로컬 PDF/HTML 보고서 | 읽기·인쇄·선택 전달에 편리 | 파일 복사·전달 시 통제 약화; 일반 출력 파일은 자체 접근 제어 없음 | 필요한 세트의 결과 내보내기 |
| Google Docs | 웹 접근·공동 검토·보고서 편집에 편리 | Google 서버 저장·계정/공유 권한·타인 복사·조직 정책을 고려 | 필요한 요약의 선택 공유 |
| 다른 클라우드 문서 서비스 | 협업 기능을 선택 가능 | 서비스만 바꾼다고 외부 저장·공유 위험이 사라지지는 않음 | 현재 추가 도입 근거 없음 |

[SQLite 공식 문서](https://www.sqlite.org/whentouse.html#application_file_format)는 데스크톱 앱의 내부 저장 용도로 설명합니다. 이는 앱 구현 제안이며 사용자가 SQLite 관리 프로그램을 설치해 조작해야 한다는 의미가 아닙니다.

Google Docs는 공식적으로 전송 중/저장 시 암호화를 제공합니다. 따라서 ‘Google Docs는 암호화가 없어 위험하다’는 평가는 맞지 않습니다. 하지만 표준 암호화가 곧 Google조차 내용을 볼 수 없는 종단 간 암호화를 뜻하지는 않습니다. [Google Docs 개인정보 안내](https://support.google.com/docs/answer/10381817?hl=en), [별도 클라이언트 측 암호화 조건](https://support.google.com/drive/answer/10519333?hl=en)

별도 클라이언트 측 암호화에는 지원되는 Workspace 계정·관리자 설정 등이 필요합니다. 현재 계정 유형·설정은 확인하지 않았습니다. [공유 설정](https://support.google.com/docs/answer/2494822?hl=en)에 따라 ‘링크가 있는 모든 사용자’가 접근할 수 있으므로 필요한 계정만 지정하는 운영이 필요합니다. 실제 Google 계정·문서는 열거나 변경하지 않았습니다.

### 이 프로젝트에 대한 추천

**원본 스캔·답지·채점 원장은 로컬, Google Docs는 선택한 요약의 공유용**으로 두는 안을 추천합니다. 외부 서버로 학생 원본을 보내지 않는 것이 최우선일 때 적합한 선택이며 모든 위협에서 로컬이 무조건 안전하다는 뜻은 아닙니다.

후속 질문처럼 **기록까지 외부 송출 없이** 운영한다면 Google Docs 업로드도 제외해야 합니다. Google Docs를 사용하는 선택 기능은 그 조건의 별도 예외를 사용자가 허용할 때에만 검토합니다. 기본 추천은 앱 내부 저장·조회와 로컬 PDF/HTML 내보내기입니다. 클라우드 문서의 암호화가 ‘외부 전송 없음’을 의미하지는 않습니다.

- 앱 데이터는 Git 저장소 및 자동 클라우드 동기화 폴더 밖에 저장하는 기본안을 제안합니다. GitHub에는 코드·비식별 시연·검증 요약만 둡니다.
- PC/백업의 암호화와 복구를 함께 설계합니다. SQLite 저장만으로 암호화가 생기지 않으므로 별도 저장 암호화가 필요합니다. [SQLite 암호화 확장](https://www.sqlite.org/see/doc/trunk/www/readme.wiki)
- Windows 드라이브 암호화는 분실된 저장장치의 노출 완화 수단입니다. 로그인된 PC의 악성코드·공유 실수까지 해결하지는 않습니다. 현재 PC의 설정을 확인하거나 변경하지 않았습니다. [Microsoft BitLocker 개요](https://learn.microsoft.com/en-us/windows/security/operating-system-security/data-protection/bitlocker/index)
- 백업에는 원본·기록·암호화 키 복구 방식을 포함하고 복원 시험을 합니다. 로컬 저장만 하고 백업하지 않으면 자료 유실 위험이 남습니다.
- 공유 시 학생 식별 정보와 원본 이미지를 필요한 범위로 줄이고 대상 계정·항목을 확인합니다. 실명만 지웠다고 완전한 익명 자료라고 보장하지 않습니다.
