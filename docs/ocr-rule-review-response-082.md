## A02 — 학생 폴더·답지 파일·원본 파일을 직접 지정

사용자 확정 요구로 반영했습니다. 신규 원자료 준비 진입점 `tools/prepare_ocr_sources.py`는 학생 폴더, 원본 PDF, 답지 PDF를 필수 인자로 받습니다. 파일명 검색/후보 우선순위/다운로드 폴더 자동 선택은 없습니다. 지정 파일이 없으면 중단합니다. 원본과 답지의 출처·사본·해시를 분리합니다. 한 PDF에 문제와 답지가 함께 있으면 동일 파일을 두 역할로 직접 지정할 수 있습니다.

답지 시작 페이지도 명시적으로 받으며 지정한 답지 문서에서만 읽습니다. 문항/정답 해석기는 여전히 기존 교재 형식 전용이므로 다른 자료의 범용 파싱 완료가 아닙니다. 최종 앱에서는 폴더/파일 선택 창으로 제공할 요구사항이며, 이번에 데스크톱 UI나 패키징을 만든 것은 아닙니다. 독립 실행·외부 전송 없음 조건과 충돌하지 않습니다.

개발 실행 형식 (경로는 예시):

```powershell
python -m tools.prepare_ocr_sources --student-dir "D:/inputs/student" --original "D:/inputs/original.pdf" --answer-key "D:/inputs/key.pdf" --key-first-page 1 --config "D:/inputs/mapping.json" --set-id C --output "private/new-source"
```

## A03 — 회색조와1334×1888의 이유

회색조는 색 대신 밝기 한 값으로 정렬·획 검출·원본 차이를 계산하기 위한 처리입니다. 연산/메모리를 줄이고 현재의 밝기 기준 마스크와 맞지만, OCR 일반의 필수 조건은 아닙니다. 서로 다른 색도 비슷한 회색으로 바뀔 수 있어 색 구분 정보는 잃습니다. 현재 고해상도 처리도 회색조이므로 색 정보가 복구되는 것은 아닙니다.

1334×1888은 원본과 학생 자료를 같은 좌표계에서 비교하는 작업 크기입니다. A4에 가까운 세로 비율이며 전체 페이지 계산량을 줄입니다. 그러나 정확히 이 수치가 최적이라는 비교시험/선정 근거는 확인되지 않았습니다. 다른 종이 비율까지 이 크기로 강제 변환하면 비율이 변할 수 있습니다. 다른 좌표·픽셀 임계값도 이 크기에 묶여 있으므로 크기만 바꾸면 동작이 달라집니다.

## A04 — 문항번호를 OCR로 읽어 찾을 수 있나?

여기서 숫자는 문항번호가 맞습니다. 현재는 PDF 텍스트층과 문자 좌표를 직접 읽습니다. 로컬 OCR의 글자 검출·인식을 통해 번호와 위치를 얻고, 두 단 배치·번호 형태·주변 위치·순서로 후보를 구분하는 코드를 붙이는 구현은 가능합니다. OCR 자체가 문항번호와 지문 속 숫자를 확실히 구분해 주는 것은 아닙니다. 현재 사용하는 TextRecognition은 이미 잘라낸 이미지를 읽는 단계라 전체 페이지 검출/구획 기능을 추가해야 합니다. 이 대체 경로는 아직 구현·정확도 검증되지 않았으며, 생성형AI/외부 전송은 필수 조건이 아닙니다.

## A06 — 두 단은 유지하되 상하좌우 경계가 꼭 필요한가?

문항별 채점을 위해 영역의 소속을 나누는 것은 필요하지만 고정 여백을 잘라 버리는 방식이 필수는 아닙니다. 좌우50픽셀은 바깥 여백 제외, 중앙667은 두 단 분리, 제목보다18픽셀 위는 문항 시작 여유, 다음 제목18픽셀 위는 다음 문항 침범 방지, 마지막1738은 하단150픽셀 제외로 작동합니다. 정확한 여유값은 Codex 선택입니다.

특히 마지막 하단150픽셀 배제는 학생 필기를 지워도 된다는 근거가 없고 q39 잘림을 일으켰습니다. 개선 방향은 두 단 구조를 유지하며 바깥쪽은 페이지 끝까지 후보를 살리고, 문항 사이에서는 연결된 학생 획과 문항 소속을 별도로 판단하는 것입니다. 이는 제안이며 이번 턴에서 경계를 일괄 변경하지 않았습니다. 단순히 모든 문항 경계를 없애면 다른 문항의 답이 섞일 수 있습니다.

## A07 — 밑줄3개 이상,2개는?

현재 정규식은 텍스트층의 `_`가3개 이상 연속인 경우만 빈칸으로 등록합니다.2개는 이 빈칸 목록에서 빠집니다. ‘충분히 긴 빈칸’을 찾는 임시 조건으로 볼 수 있지만3개가 맞다는 검증은 없습니다. PDF에 그림/선으로 그린 밑줄은 이 조건만으로 찾지 못합니다. 또한 현재C 객관식 경로는 이 빈칸 목록을 조각 생성에 쓰지 않으므로 이 규칙이 해당 학생 밑줄을 삭제한 원인은 아닙니다.

## A08 — SIFT / RANSAC

SIFT는 두 이미지에서 같은 위치를 찾아 연결할 수 있도록 글자 모서리 같은 특징점을 찾고 표현하는 방법입니다. RANSAC은 그 연결 중 잘못된 짝을 걸러내면서 다수의 연결에 맞는 변환을 추정합니다. 현재는 학생 스캔을 원본 문제 위에 겹치도록 페이지 전체에 한 변환을 적용합니다. 글자를 읽거나 채점하는 기능이 아니며 국소 구김은 별도입니다.6000/0.7/3 역시 현재 설정이지 사용자 확정 수치가 아닙니다.

기술 근거: [OpenCV 공식 특징 매칭/호모그래피 설명](https://docs.opencv.org/4.12.0/d1/de0/tutorial_py_feature_homography.html).

## A09 — 답지와 문제지가 안 맞았을 때의 규칙인가?

아닙니다. 학생 스캔과 원본 문제 이미지의 위치 정렬을 검사합니다. 서로 다른 페이지, 심한 훼손, 특징 부족 등에서 중단할 수 있습니다. 같은 레이아웃의 다른 페이지도 일부 잘 맞을 수 있으므로 문서 내용 일치 보증은 아닙니다. 답지 문항ID와 문제 문항ID의 일치 검사는 별도이고, 그것도 정답 내용의 올바름까지 증명하지는 않습니다.30개/3픽셀은 설정 기준이며 각 글자의 정렬을 보장하지 않습니다.

## A10 — 고해상도에도 같은 변환을 적용하는 이유

작은 이미지에서 비교/위치 계산을 수행하고, 실제 OCR 조각은 고해상도 학생 이미지에서 가져와 획 세부를 유지하려는 구조입니다. 작은 좌표의 변환을 큰 좌표에 맞춰 환산해야 같은 위치를 가져올 수 있습니다. 회전·이동으로 내용이 없는 테두리가 생길 때 흰색으로 채우는 것은 검은 테두리가 필기로 검출되는 것을 피합니다. 스캔 밖이나 문항 경계 밖에서 잃은 필기를 복원하지는 않습니다. 크기 변환·보간 자체의 손실 가능성은 남습니다.
